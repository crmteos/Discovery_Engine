# Специфікація підсистеми PROJECT_CONTEXT.md, шаблони LibreOffice UNO API та Огляд інструментів візуалізації Discovery Engine

## 1. Архітектурна підсистема оперативної пам'яті PROJECT_CONTEXT.md

### 1.1 Мета та місце підсистеми у трирівневій пам'яті
У складних ШІ-проєктах, таких як **Discovery Engine**, покладатися виключно на оперативне контекстне вікно чат-сесії є архітектурною помилкою. Оскільки великі мовні моделі (LLM) позбавлені біологічного механізму консолідації довгострокової пам'яті, накопичення неструктурованого чат-анамнезу призводить до розмивання ваг уваги (**Attention Weight Dispersion**) під час авторегресійної генерації.

Для розв'язання цієї проблеми впроваджується трирівнева система зовнішньої пам'яті:
1. **PROJECT_SPEC.md** — Незмінне джерело правди (*Single Source of Truth*): архітектурні межі, стек, протоколи взаємодії та критерії готовності (DoD).
2. **PROJECT_STATE.md** — Динамічний лог стану: поточний фазовий статус розробки, журнал останніх змін, активні модулі та блокери.
3. **PROJECT_CONTEXT.md** — Буфер оперативної пам'яті та активний векторний граф джерел знань: забезпечує ізольоване керування інформаційними потоками, нормалізацію контекстного вікна та санітизацію контекстного шуму перед передачею токенів у модель.

### 1.2 Механізм запобігання когнітивним пасткам ШІ
Підсистема `PROJECT_CONTEXT.md` безпосередньо нейтралізує наступні когнітивні пастки:
* **Неявний контекст та засліплення уваги (Fixed Attention Bias)**: При збільшенні довжини контексту позиційні кодування (зокрема RoPE — Rotary Position Embedding) втрачають здатність пригнічувати віддалений шум. `PROJECT_CONTEXT.md` проводить жорстке відсікання застарілих historical-токенах і подає лише релевантні фрагменти джерел знань.
* **Дифузія параметрів**: Запобігає несанкціонованому витягуванню застарілих структур даних із попередніх етапів діалогу за рахунок явного токенного нормування.
* **Зациклення на хаотичному налагодженні (Chaotic Debugging)**: Очищує оперативний контекст від емоційних промптів та хаотичних спроб дебагінгу, формуючи виключно мінімальний відтворюваний приклад (Minimal Reproducible Example).

### 1.3 Алгоритм санітизації та токенного нормування
Процес оновлення `PROJECT_CONTEXT.md` перед кожною чат-сесією або транзакцією інференсу підпорядковується п'яти крокам:
1. **Ізоляція активного завдання**: Витяг з `PROJECT_STATE.md` поточного фокусного модуля та цільової метрики.
2. **Фільтрація джерел знань**: Семантичний відбір лише тих сегментів баз знань (Knowledge Bases), які мають безпосереднє відношення до поточного завдання.
3. **Обрізання токенного оверхеду**: Загальний обсяг `PROJECT_CONTEXT.md` не повинен перевищувати 2,000–3,000 токенів.
4. **Видалення мета-шуму**: Повне відсікання ввічливостей, обговорень та проміжних некоректних варіантів коду.
5. **Сінхронізація з IDE / LibreOffice**: Збереження структурованого маркдаун-файлу у корінь проєкту для зчитування розширеннями та ШІ-агентами.

## 3. Технічна реалізація фреймворку в LibreOffice: Python UNO API та .oxt Розширення

### 3.1 Архітектура з'єднання LibreOffice з ШІ-моделями
LibreOffice надає вбудоване Python-середовище та універсальний об'єктний інтерфейс **UNO API (Universal Network Objects)**. Це дозволяє створювати автономні розширення (`.oxt`), які перетворюють LibreOffice Writer або Calc на інтерактивне середовище розробника та управління проєктом Discovery Engine.

Для створення безкоштовної та надійної інфраструктури розробки використовуються наступні інструменти:
* **APSO (Alternative Script Organizer for Python)**: Офіційне розширення для LibreOffice, яке дозволяє зручно редагувати, запускати та налагоджувати Python-скрипти всередині офісного пакета.
* **LiteLLM / Ollama API**: Локальний або уніфікований проксі-сервер для виклику LLM (Gemini, Claude, Llama 3) через стандартний REST API.
* **UNO Runtime Environment (URE)**: Модуль Python, який надає доступ до активних документів Writer (`com.sun.star.text.TextDocument`) та таблиць Calc (`com.sun.star.sheet.SpreadsheetDocument`).

### 3.2 Структура пакета розширення LibreOffice (.oxt)
Пакунок розширення LibreOffice являє собою стандартний ZIP-архів із розширенням `.oxt`, який містить таку структуру:
```text
discovery_engine_copilot.oxt
├── META-INF/
│   └── manifest.xml          # Опис точок входу та файлів розширення
├── Addons.xcu                 # Опис меню, кнопок та пунктів бічної панелі (Sidebar)
├── python/
│   └── main_copilot.py        # Основний код інференсу та обробки UNO API
├── pythonpath/
│   └── context_manager.py    # Модуль читання PROJECT_CONTEXT.md та санітизації
└── description.xml            # Метадані розширення (версія, автор, назва)
```

## 4. Працездатний шаблон Python-скрипта для розширення LibreOffice

Нижче наведено повністю працездатний Python-скрипт, який реалізує читку файлів трирівневої пам'яті (`PROJECT_SPEC.md`, `PROJECT_STATE.md`, `PROJECT_CONTEXT.md`), формування відсанітизованого промпту, виклик LLM та вставку згенерованого результату в активне вікно LibreOffice Writer чи Calc.

```python
import uno
import unohelper
import urllib.request
import json
import os

PROJECT_ROOT = "/workspace"
FILE_SPEC = os.path.join(PROJECT_ROOT, "PROJECT_SPEC.md")
FILE_STATE = os.path.join(PROJECT_ROOT, "PROJECT_STATE.md")
FILE_CONTEXT = os.path.join(PROJECT_ROOT, "PROJECT_CONTEXT.md")

LLM_API_URL = "http://localhost:11434/api/generate"
MODEL_NAME = "llama3:latest"

class MemorySanitizer:
    @staticmethod
    def read_file_safe(path):
        if os.path.exists(path):
            with open(path, "r", encoding="utf-8") as f:
                return f.read()
        return ""

    @classmethod
    def build_sanitized_prompt(cls, user_query):
        spec = cls.read_file_safe(FILE_SPEC)
        state = cls.read_file_safe(FILE_STATE)
        context = cls.read_file_safe(FILE_CONTEXT)

        system_instructions = (
            "ТИ — СУВОРЕ СЕРЕДОВИЩЕ СИСТЕМНОЇ АРХІТЕКТУРИ ТА ПРОВІДНИЙ ІНЖЕНЕР ШІ.\n"
            "ПРАВИЛА: Категорична заборона використання першої особи ('Я'), заборона ввічливостей.\n"
            "Відповіді мають бути транзакційними, без галюцинацій та без повного перепису коду.\n"
        )

        full_prompt = (
            f"{system_instructions}\n\n"
            f"=== PROJECT_SPEC.md ===\n{spec[:1500]}\n\n"
            f"=== PROJECT_STATE.md ===\n{state[:1000]}\n\n"
            f"=== PROJECT_CONTEXT.md ===\n{context[:2000]}\n\n"
            f"=== ЗАПИТ КОРИСТУВАЧА ===\n{user_query}\n\n"
            f"=== ВІДПОВІДЬ (СТРИМКІ ТЕХНІЧНІ ДІЇ/ДИФИ) ==="
        )
        return full_prompt

def run_discovery_copilot(*args):
    desktop = xsCRIPTCONTEXT.getDesktop()
    model = desktop.getCurrentComponent()

    if not model:
        return

    if hasattr(model, "Text"):
        controller = model.getCurrentController()
        selection = controller.getSelection()
        selected_range = selection.getByIndex(0)
        user_query = selected_range.getString()

        if not user_query.strip():
            user_query = "Проаналізувати поточну конфігурацію проєкту та надати рекомендації."

        sanitized_prompt = MemorySanitizer.build_sanitized_prompt(user_query)

        try:
            payload = {
                "model": MODEL_NAME,
                "prompt": sanitized_prompt,
                "stream": False,
                "options": {"temperature": 0.1, "num_ctx": 4096}
            }
            req = urllib.request.Request(
                LLM_API_URL,
                data=json.dumps(payload).encode("utf-8"),
                headers={"Content-Type": "application/json"}
            )
            with urllib.request.urlopen(req) as response:
                res_data = json.loads(response.read().decode("utf-8"))
                ai_response = res_data.get("response", "Помилка: Відповідь порожня.")

        except Exception as e:
            ai_response = f"\n[Помилка інференсу LLM API: {str(e)}]\n"

        text = model.Text
        cursor = text.createTextCursorByRange(selected_range.getEnd())
        text.insertString(cursor, f"\n\n--- [Discovery Engine AI Response] ---\n{ai_response}\n", False)

g_exportedScripts = (run_discovery_copilot,)
```

## 5. Порівняльний аналіз та вибір інструментів візуалізації для Discovery Engine

Для забезпечення ефективного спостереження, моніторингу та представлення результатів **Discovery Engine** (агрегація баз знань, гармонізація даних, навчання моделей та вихід в API/CLI) необхідно вибрати оптимальний стек інструментів візуалізації.

### 5.1 Класифікація інструментів візуалізації за рівнями системи

1. **Рівень 1: Офісні та десктопні інструменти (LibreOffice Ecosystem)**:
   - **LibreOffice Calc + LibreCharts**: Для табличного аналізу гармонізованих баз знань, аналізу помилок за тестами та побудови діаграм типу think-cell.
   - **LibreOffice Draw / Writer**: Для ведення архітектурних діаграм та звітів специфікації.

2. **Рівень 2: Спеціалізовані AI Observability & Embedding Visualizers**:
   - **Arize Phoenix**: Векторні простори 2D/3D UMAP/t-SNE, трасування запитів та оцінка галюцинацій (LLM-as-a-judge).
   - **MLflow AI Observability**: Моніторинг затримок, витрат токенів та автологування DAG-агентів.

3. **Рівень 3: Інтерактивні Web UI & Data Dashboards**:
   - **Streamlit / Gradio**: Для швидкого побудови прототипу та інтерактивного майданчика (Playground).
   - **React + D3.js / Chart.js**: Для повноцінної продакшн-консолі з високим рівнем індивідуалізації.

### 5.2 Детальний порівняльний аналіз візуалізаційних технологій

| Категорія інструменту | Назва інструменту | Основне призначення у Discovery Engine | Переваги | Обмеження |
| :--- | :--- | :--- | :--- | :--- |
| **Офісна візуалізація** | **LibreOffice Calc + LibreCharts** | Табличний аналіз метрик, розрахунок бюджетів, діаграми типу think-cell. | $0 бюджет, нативна робота з Markdown/CSV, відсутність сторонніх хмар. | Не підходить для реального часу (>100 RPS) та 3D векторних просторів. |
| **AI Observability** | **Arize Phoenix** | Візуалізація векторних кластерів баз знань (t-SNE/UMAP), відстеження дрейфу даних. | Відкритий код, підтримка OpenTelemetry, вбудована аналітика галюцинацій. | Вимагає окремого запуску сервера або Docker-контейнера. |
| **Пайплайн-моніторинг** | **MLflow AI Platform** | Трекінг метрик навчання (Loss, Accuracy, Perplexity), логування експериментів. | Стандарт індустрії, багатий Python SDK (`mlflow.autolog()`), Model Registry. | Фокусується більше на метриках, ніж на UX взаємодії з людиною. |
| **Python Web UI** | **Streamlit / Gradio** | Інтерактивний майданчик (Playground) для тестування запитів та відображення карт уваги. | Швидкість розробки (чистий Python), сотні готових віджетів. | Обмежена кастомізація складних анімацій порівняно з JS-фреймворками. |
| **Custom Web UI** | **React + D3.js / Chart.js** | Повноцінна веб-консоль Discovery Engine для зовнішніх клієнтів та API-моніторингу. | Повний контроль над UX, найвища швидкість відмалювання (WebGL/SVG). | Висока трудоємність розробки, потреба у фронтенд-інженерах. |

### 5.3 Підсумкові рекомендації щодо вибору стеку візуалізації

Для Discovery Engine рекомендується застосувати **комбінований підхід (Hybrid Stack)**:

1. **Для фази розробки, відлагодження та $0 бюджету (Локальний контур)**:
   - Використовувати **LibreOffice Calc** (з плагіном APSO/LibreCharts) для ведення таблиць гармонізації та перевірки схем даних.
   - Використовувати **Arize Phoenix (OSS)** для візуалізації 2D/3D простору векторних ембеддінгів та перевірки того, як різнопрофільні бази знань групуються в кластери.

2. **Для фази тестування та демо-прототипу (Інтерактивний Playground)**:
   - Використовувати **Streamlit** для збірки швидкої панелі перевірки інференсу з віджетами зміни гіперпараметрів та відображенням посилань на джерела (Source Citations).

3. **Для фази продакшн-розгортання та API/CLI клієнтів**:
   - Інтегрувати **MLflow** для автоматичного трасування викликів моделі та моніторингу затримок.
   - Створити кастомну веб-панель на **React + D3.js** для клієнтського контролю розгортання та видачі API-ключів.
