# DISCOVERY ENGINE: Фреймворк візуалізації, спостережуваності та Human-AI інтерфейсів

Цей документ визначає сувору інженерну специфікацію, стандарти візуалізації, інфраструктуру спостережуваності (AI Observability) та покроковий план розгортання інтерфейсів для проєкту **Discovery Engine**. Документ розроблено на основі синтезу галузевих стандартів Human-AI Interaction (Microsoft HAX, Google PAIR, ISO/IEC, NIST, IEEE), архітектурних рішень спостережуваності LLM та агентних систем (MLflow, Arize Phoenix, OpenTelemetry), методології детермінованого розроблення ШІ («Калібратор») та класичної фундаментальної бази знань з візуалізації даних.

## 1. Концептуальні засади та трирівнева архітектура пам'яті (Memory & Context Architecture)

### 1.1. Мета та принципи детермінованого розроблення ШІ-систем

Головною метою цього фреймворку є створення універсального, формалізованого середовища для проектування, візуалізації та моніторингу пайплайнів проєкту **Discovery Engine**. ШІ-модель сприймається виключно як статистично-інференційний обчислювальний блок. Для забезпечення вимірності, прозорості та детермінованого розроблення впроваджуються чотири фундаментальні принципи:

*   **Раціональність**: Повне виключення суб'єктивних інтерпретацій, атрибуції свідомості чи емоційних характеристик алгоритму.
*   **Системний контроль контексту**: Ізольоване керування інформаційними потоками, нормування контекстного вікна та зовнішня фіксація стану системи на кожному етапі розробки.
*   **Жорсткий розподіл функцій**: Чітке розмежування обов'язків між людиною (Головним системним архітектором), чат-сесією (середовищем аналізу) та IDE/код-асистентами (виконавчими модулями).
*   **Відсутність емоційного шуму**: Ліквідація компліментарності, фатичних виразів та угодливості для досягнення максимальної швидкості та точності інженерії.

### 1.2. Трирівнева архітектура зовнішньої пам'яті: PROJECT_SPEC, PROJECT_STATE, PROJECT_CONTEXT

Великі мовні моделі (LLM) позбавлені біологічних механізмів консолідації довгострокової пам'яті. Використання оперативного контекстного вікна чату як єдиного сховища знань є архітектурною помилкою через розмивання ваг уваги під час авторегресійної генерації (RoPE attention dispersion). Для вирішення цієї проблеми проєкт Discovery Engine використовує **трирівневу зовнішню пам'ять**:

| Підсистема пам'яті | Носій / Файл | Характер знань | Функціональне призначення та вміст |
| :--- | :--- | :--- | :--- |
| **1. Специфікація** | `PROJECT_SPEC.md` | Статичний (Single Source of Truth) | Незмінні архітектурні рамки, цільові метрики, технологічний стек, обмеження $0 бюджету, протоколи промптингу, рішення ADR (Architecture Decision Records) та критерії готовності (DoD). |
| **2. Динамічний стан** | `PROJECT_STATE.md` | Динамічний (Оновлюється щокроку) | Поточна фаза розробки, відсоток прогресу, лог останніх змін (Changelog), оцінка токенного оверхеду, журнал активних блокерів (Known Issues) та тригери очищення контексту. |
| **3. Доменний контекст** | `PROJECT_CONTEXT.md` / `PROJECT_CONTEXT` | Оперативно-доменний (Контекст баз знань) | Схема гармонізації баз знань Discovery Engine, картографія векторних просторів (ембеддінг-кластери), індекс активних джерел, системні промпт-шаблони та лог сесійного контекстного буфера. |

### 1.3. Деантропоморфізація та нейтралізація когнітивних пасток

Фреймворк регламентує детерміновану нейтралізацію п'яти ключових когнітивних пасток у контурі «людина-ШІ»:

1.  **Anthropomorphism & Empathy Bias (Пастка №1)**: Заборонено використання моделлю першої особи («Я», «Мій») та суб'єктивних когнітивних дієслів («думати», «розуміти», «знати»). Вони замінюються інженерними еквівалентами: *«обчислювати»*, *«аналізувати»*, *«генерувати»*, *«виводити»*.
2.  **Implicit Context & Fixed Attention Bias (Пастка №2)**: При досягненні 15–20 транзакцій або зміні модуля примусово ініціалізується нова чат-сесія з прочитанням файлів стану, що запобігає розмиванню ваг уваги (RoPE dispersion).
3.  **Sycophancy & Automation Bias (Пастка №3)**: Призначення моделлю ролі суворого аудитора. Заборонено погоджуватися з твердженнями користувача без надання логічного чи математичного доказу (Proof). При відсутності даних модель зобов'язана прямо декларувати: *«Дані відсутні в наданому контексті»*.
4.  **Chaotic Debugging & Generalist Trap (Пастка №4)**: Негайне переривання сесії при виникненні циклічних помилок, створення Minimal Reproducible Example та надання точкових кодових дифів (Strict Code Diff Rule).
5.  **Memory Architecture Deficit (Пастка №5)**: Обов'язкова синхронізація результатів виконання кожної задачі у файлах `PROJECT_STATE.md` та `PROJECT_CONTEXT.md`.

## 2. Стандарти взаємодії та дизайн-паттерни (Human-AI UX & Standardization Framework)

### 2.1. Наукові принципи Microsoft HAX Toolkit

Дизайн інтерфейсів Discovery Engine спирається на 18 вимірюваних принципів Microsoft HAX (Human-AI Interaction), що охоплюють чотири фази взаємодії:

*   **Початкова фаза (Initial Stage)**:
    *   *G1: Чіткість функціоналу*: Чітке демонстрування можливостей системи Discovery Engine.
    *   *G2: Чіткість точності*: Демонстрація можливих межевих помилок та рівня впевненості.
*   **Під час взаємодії (During Interaction)**:
    *   *G3: Контекстна своєчасність*: Надання сервісів залежно від поточного завдання користувача.
    *   *G4: Контекстна релевантність*: Відображення лише актуальної інформації.
    *   *G5: Відповідність соціальним нормам*: Дотримання очікуваного культурного та професійного контексту.
    *   *G6: Нівелювання соціальних упереджень*: Запобігання стереотипам у мові та поведінці ШІ.
*   **При виникненні помилок (When Wrong)**:
    *   *G7: Просте викликання*: Легкий запуск додаткових аналітичних сервісів.
    *   *G8: Просте відхилення*: Швидке закриття небажаних рекомендацій.
    *   *G9: Зручне виправлення*: Легке редагування та корекція помилкових висновків моделі.
    *   *G10: Обмеження сфер дій при невизначеності*: Градаційне зниження рівня автоматизації.
    *   *G11: Пояснюваність причин*: Відображення пояснень, чому система прийняла конкретне рішення.
*   **Упродовж тривалого часу (Over Time)**:
    *   *G12: Збереження нещодавніх взаємодій*: Підтримка короткострокової пам'яті сесії.
    *   *G13: Навчання на поведінці*: Персоналізація досвіду на основі дій користувача.
    *   *G14: Обережне оновлення*: Лімітування диструктивних змін при адаптації UI.
    *   *G15: Заохочення деталізованого зворотного зв'язку*: Забезпечення кнопок оцінки та корекції.
    *   *G16: Демонстрація наслідків дій*: Негайне відображення впливу рішень користувача на майбутнє навчання.
    *   *G17: Глобальні налаштування*: Надання загального контролю над параметрами моніторингу.
    *   *G18: Сповіщення про зміни*: Інформування про оновлення можливостей моделей та алгоритмів.

### 2.2. Паттерни Google PAIR (People + AI Guidebook)

Інтерфейс проєкту реалізує ключові паттерни Google PAIR для оптимізації довіри та прозорості:

*   **Explain for Understanding, Not Completeness**: Інтерфейс не повинен перевантажувати користувача повним математичним описом нейромережі. Пояснення мають бути локальними, орієнтованими на поточний вибір даних та зрозумілими для верифікації.
*   **Calibrated Trust**: Надання користувачеві індикаторів упевненості моделі (Confidence Displays), що запобігає надмірній довірі (Over-trust) або безпідставному відхиленню результатів (Under-trust).
*   **Balance Automation vs. Augmentation**: Автоматизація застосовується для рутинних задач агрегації та первинного збору даних, тоді як стратегічний вибір архітектури та підтвердження релізів залишаються за людиною-архітектором.
*   **Feedback & Human-in-the-Loop Loops**: Кожна дія з коригування результатів в UI перетворюється на тестовий прецедент для подальшого оцінювання (Evaluation Dataset).

### 2.3. Міжнародні стандарти та нормативні рамки (ISO/IEC, NIST, IEEE)

Розгортання інтерфейсів Discovery Engine узгоджується з міжнародними стандартами:

*   **ISO 9241 (Parts 110, 112, 210, 810)**: Принципи ергономіки взаємодії, подачі інформації та стандарти людяно-центричного проектування (Human-Centred Design).
*   **ISO/IEC JTC1/SC42 (ISO/IEC 22989, TR 24028, TR 24027, TS 8200)**: Стандарти надійності, прозорості, вимірювання упередженості та керованості (Controllability) автоматизованих ШІ-систем.
*   **NIST AI Risk Management Framework (AI RMF 1.0)**: Управління ризиками безпеки, прозорості та справедливості ШІ-рішень.
*   **IEEE P7000–P7010**: Стандарти етичного проектування, прозорості автономних систем (P7001), обробки даних (P7002) та вимірювання людського благополуччя (P7010).

## 3. Специфікація підсистем та UI-модулів Discovery Engine

Система візуалізації Discovery Engine будується як чотиримодульна панель управління.

### 3.1. Модуль 1: Data Hub & Harmonization Pipeline (Агрегатор та Спільний знаменник)

*   **Панель підключених джерел**: Графічне відображення різнопрофільних баз знань (БД, веб-ресурси, структуровані документи, PDF) з індикаторами статусу синхронізації та обсягу токенів.
*   **Схема гармонізації (Harmonization Workflow)**: Наочна візуалізація пайплайну приведення даних до єдиної структури: очищення, токенізація, генерація ембеддінгів та побудова Графу Знань (Knowledge Graph).
*   **2D/3D Векторний простір (Embedding Projector)**: Інтерактивна візуалізація векторного простору знань з використанням алгоритмів пониження розмірності **t-SNE** та **UMAP**. Дозволяє спостерігати, як різнородні бази знань зближуються до «спільного знаменника» та формують тематичні кластери.

### 3.2. Модуль 2: Training & Fine-Tuning Studio (Студія підготовки та навчання)

*   **Моніторинг метрик у реальному часі**: Динамічні графіки функції втрат (**Loss**), перплексії (**Perplexity**), швидкості навчання (**Learning Rate**) та показника відповідності першоджерелам (**Grounding Rate**).
*   **Графіки дрейфу даних (Data Drift & Bias)**: Візуальне порівняння розподілу вхідних токенів та оцінка відхилення знань у часі.
*   **Матриця суперечностей та оцінка кластерів**: Графічне виявлення дубльованих або конфліктних фактів між різними агрегованими базами знань.

### 3.3. Модуль 3: Traceability & Playground Studio (Трасування та Інтерпретація)

*   **Дерево трасування запитів (Execution & Agent Traces)**: Гранульована візуалізація кожного кроку виконання за стандартом OpenTelemetry — від збору токенів, викликів інструментів (Tool Calls) до формування остаточної відповіді.
*   **Трасування джерел (Source Citation & Grounding)**: Підсвічування конкретних фрагментів баз знань, з яких модель витягла факти для відповіді, з можливістю швидкого переходження до першоджерела.
*   **Індикатор упевненості (Confidence Score Display)**: Графічне відображення ймовірнісної упевненості моделі в згенерованому фрагменті.
*   **Панель двоїстого зворотного зв'язку (Human Feedback Loop)**: Інструменти для прийняття, коригування або позначення галюцинованих відповідей із автоматичним збереженням прецедентів у тестовий датасет (Evaluation Dataset).

### 3.4. Модуль 4: API & CLI Management Center (Центр розгортання та телеметрії)

*   **Моніторинг API та навантаження**: Графіки запитів на секунду (RPS), системної затримки (Latency - TTFT/TBT) та споживання ресурсів сервера.
*   **Контроль токенного бюджету та витрат**: Деталізований облік витрат токенів за моделями та етапами пайплайну.
*   **Термінал керування CLI**: Готові інструменти та команди для запуску інференсу через консольний інтерфейс (наприклад, `discovery-cli query "..."`).

### 5.1. Фаза 1: Ініціалізація інфраструктури пам'яті та телеметрії (Traces & Memory Bootstrapping)

1.  **Формування потрійного контуру пам'яті**:
    *   Створити файл `PROJECT_SPEC.md` із зазначенням архітектурних меж, стеків ($0 budget), протоколу деантропоморфізації та критеріїв DoD.
    *   Створити файл `PROJECT_STATE.md` для динамічного трекінгу статусу розробки та журналу блокерів.
    *   Створити файл `PROJECT_CONTEXT.md` для збереження картографії баз знань, ембеддінг-просторів та системних промптів.
2.  **Підключення телеметрії виконання (OpenTelemetry & MLflow / Phoenix)**:
    *   Ініціалізувати інструментарієве автологігування (наприклад, `mlflow.openai.autolog()` або `npx @arizeai/phoenix-cli setup`).
    *   Забезпечити ізольоване збереження трасів без витоку приватних токенів та персональних даних.

### 5.2. Фаза 2: Розгортання модулів агрегації та гармонізації даних (Data Hub)

1.  **Розробка інтерфейсу джерел та графа знань**:
    *   Створити компоненти відображення статусу підключених джерел (БД, PDF, Веб).
    *   Реалізувати візуальний пайплайн гармонізації (очищення -> токенізація -> векторизація -> спільний знаменник).
2.  **Інтеграція векторного проєктора (t-SNE / UMAP Projector)**:
    *   Впровадити віджет 2D/3D відображення векторних ембеддінгів за рекомендаціями Бен Фрая та Натана Яу (Книги №2, №10).
    *   Забезпечити підсвічування кластерів різних баз знань для перевірки їхнього зближення.

### 5.3. Фаза 3: Впровадження студії спостережуваності та оцінки якості (Observability & Traceability)

1.  **Побудова дерев трасування (Agent Execution DAG Traces)**:
    *   Розробити інтерактивне дерево виконання запиту (від prompt input, retrieval steps, tool calls до llm response).
    *   Реалізувати віджети трасування джерел (Source Citations) з прямим посиланням на першоджерело за принципом *Explain for Understanding* (Google PAIR).
2.  **Розгортання оцінювачів якості (Evaluators)**:
    *   Впровадити автоматичні метрики Grounding Rate (відсутність галюцинацій) та оцінювачі LLM-as-a-judge.
    *   Створити візуальні графіки дрейфу знань та точності моделей згідно зі стандартами ISO/IEC TR 24028.

### 5.4. Фаза 4: Запуск інтерактивного Playground та інтеграція API/CLI

1.  **Розробка інтерфейсів перевірки та Human-in-the-Loop**:
    *   Реалізувати інтерактивний Playground з вибором гіперпараметрів (температура, промпт-шаблони).
    *   Впровадити елементи швидкого зворотного зв'язку (G15 Microsoft HAX) для коригування відповідей людиною-архітектором.
2.  **Інтеграція Центру розгортання API & CLI**:
    *   Встановити дашборди моніторингу затримок (Latency), запитів за секунду (RPS) та фінансових/токенних витрат (Cost Telemetry).
    *   Сформувати CLI-пакет (наприклад, `discovery-cli`) з документацією та готовими командами для зовнішніх інтеграцій.
